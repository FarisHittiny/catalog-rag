# catalog-rag eval report

All numbers below come from `reports/latest.md` (run of 2026-09-16, commit d881fb1) unless a sentence names an earlier run. Corpus: 148 courses.

## What this is

An eval-driven retrieval-augmented question answering system over the 148 ECEN and CSCE course records on catalog.tamu.edu, built so that the eval harness, not the chatbot, is the product. Every retrieval and generation change was measured against a 115-question human-verified gold set before it was kept, and the ones that did not pay were reverted. This report is the record of what was tried, what each change did to the numbers, and what the numbers do not show.

## The gold set

115 questions in `data/gold/gold_set.jsonl`: 50 factual, 30 prereq, 20 multi_hop, 15 not_in_catalog. The 100 answerable rows feed the retrieval metrics; all 115 feed the generation metrics. Each row carries the course records a correct answer must draw from (`gold_course_ids`), a one or two sentence `gold_answer`, and three flags: `has_code` (the question names a course code), `paraphrase` (the question shares no vocabulary with the record), and `verified`.

Splits. `has_code` covers 84 rows (70 answerable), `no_code` 31 rows (30 answerable), `paraphrase` 15 rows (10 factual, 5 prereq). The no_code split now holds two different populations: 20 questions that quote a phrase from the course title or description ("the class on Computer Architecture and Design"), and 10 paraphrase questions that describe the course without any of its words ("the class where you build a CPU"). The paraphrase row in the table isolates the second group. The 5 prereq paraphrases name the source course by its code, so they sit in has_code and test only the router's phrasing coverage.

How rows were made. Questions were written by hand in the register a sophomore types. Draft answers were generated by a model from the course records in `courses.jsonl` (prereq_raw, credits, crosslisted, description); for "what can I take after X" questions the gold ids and answer were derived from `prereq_graph.unlocked_by(X)`. Every draft row was written with `verified: false`. Rows were then checked one at a time against the catalog page, using `eval.review`, which prints each unverified row beside its source records, and flipped to `verified: true` only after that check. `validate_gold` refuses to run the eval while any row is unverified, so no reported number has ever included a draft.

Human labels. `data/gold/human_labels.jsonl` holds 30 rows (12 factual, 8 prereq, 6 multi_hop, 4 not_in_catalog, seeded selection) with a hand-assigned correct/incorrect label against the routed retriever's generated answer. A label counts only while that exact answer is still what the retriever produces, so stale labels read as unlabeled rather than as agreement.

## Retrievers

In the order they were built. Every retriever indexes the same 148 chunks (one per course) and returns course ids, best first, deduplicated by course.

**bm25.** rank_bm25 over lowercase alphanumeric tokens of the chunk text. The baseline. A course code like "ECEN 350" becomes the two tokens "ecen" and "350", and "350" appears in every course that lists ECEN 350 or CSCE 350 as a prerequisite, so a question that names a course competes with all of that course's dependents. Overall recall@5 0.671.

**bm25_codes.** Same scoring, but the tokenizer also emits one fused token per course code ("ecen350") for both corpus and query, so "ECEN 350", "ECEN350" and "ecen 350" match the same rare token. Overall recall@5 0.756, and the gain is where the code matters: has_code 0.673 to 0.795, prereq 0.581 to 0.715. no_code is unchanged at 0.667 because those questions contain no code.

**bm25_codes_id.** bm25_codes, plus every course code named in the query is pinned to the top of the ranking in query order and removed from the tail. For a factual lookup the named course is the gold record, so factual recall@1 goes from 0.600 to 0.780 and overall recall@5 to 0.801. For "what can I take after X" the pinned X is never gold, so every dependent drops one rank: prereq recall@1 goes from 0.125 to 0.000 and prereq MRR from 0.817 to 0.489. Pinning is type-blind; that is what the router later fixes.

**dense.** BAAI/bge-small-en-v1.5 through sentence-transformers, normalized vectors, cosine by numpy dot product, bge's query-side instruction prefix. Embeddings are cached on disk keyed by a hash of the model name and every chunk. It is the only retriever that does not need the question to share a token with the record. Overall recall@5 0.567, the lowest of the five text retrievers, because 70 of the 100 answerable questions name a code and an embedding cannot match a code exactly (has_code 0.417). On the questions with no code it is the best retriever by a wide margin: no_code 0.917, paraphrase 0.711.

**hybrid.** Reciprocal rank fusion of bm25_codes and dense, RRF constant 60, 50 candidates from each, equal weight. No reranker. Overall recall@5 0.702, between its two parts. On paraphrases it reaches 0.363, not 0.711: with equal weights a course that dense ranks first and bm25_codes does not rank at all scores 1/61, while a course that both retrievers put in their top ten scores about twice that, so BM25's confident wrong answers outvote dense's right one.

**graph.** The prereq graph built from each chunk's parsed prerequisite groups (edge prereq to course). For each course code in the query it returns `unlocked_by(code)`, the direct successors, ordered by course number. It answers one kind of question and nothing else: prereq recall@5 0.761, MRR 1.000; factual 0.000. Standalone it is not a retriever, it is the prereq half of the next one.

**routed.** A rule-based router reads the question text and returns "prereq" or "other". "prereq" goes to graph, everything else to bm25_codes_id, and a prereq-routed question the graph cannot answer falls through to bm25_codes_id. Reverse-direction phrasings ("what do I need before X") are guarded to "other". For generation, a prereq-routed question hands the generator the queried course's own record followed by every graph result, with no top-5 cap; everything else gets the top 5. Overall recall@5 0.822, prereq recall@1 0.244 and MRR 0.917 against bm25_codes_id's 0.000 and 0.489, factual identical to bm25_codes_id because the route is the same.

## Findings

**Fused code tokens and id pinning.** Plain BM25 splits "ECEN 350" into "ecen" and "350", and "350" is in every dependent's prerequisite sentence, so the course a student names loses to the courses that require it. Fusing the code into one token raised overall recall@5 from 0.671 to 0.756 and prereq recall@5 from 0.581 to 0.715. Pinning the named course to rank 1 then raised factual recall@1 from 0.600 to 0.780 and overall recall@5 to 0.801. The cost is on prereq questions, where the named course is the one record that is never gold: prereq recall@1 fell from 0.125 to 0.000 and prereq MRR from 0.817 to 0.489. Pinning is right for lookups and wrong for "what comes after", and no single ranking fixes both.

**Graph route.** Sending prereq-routed questions to the graph, with the same generator, same prompt and same judge, moved prereq correctness from 0.400 (bm25_codes_id) to 0.800 (routed). Retrieval on that split went from recall@1 0.000 and MRR 0.489 to 0.244 and 0.917. The graph returns exactly the set of direct successors, so the generator sees the whole list instead of whichever five dependents scored highest on BM25.

**Retrieval improved, answers got worse, until context construction was fixed.** When generation first landed (2026-09-13, 100 questions), routed had the best retrieval numbers and prereq correctness of 0.320. Two things were wrong with what the generator was handed: the top-5 cap truncated unlock lists (12 of 25 prereq rows had more than 5 gold courses), and the graph omits the queried course itself, so the generator abstained when the course the student asked about was missing from its context. Handing it the queried course first and then every graph result took prereq correctness from 0.320 to 0.840 on that run and prereq abstention accuracy from 0.920 to 1.000. Retrieval metrics did not change; only the context did.

**Dense.** Overall recall@5 0.567, the lowest of the five text retrievers (has_code 0.417, prereq 0.272). It is also the only retriever that handles paraphrases: 0.711 on the paraphrase split against at most 0.363 for every other retriever (hybrid 0.363, bm25 and bm25_codes 0.304, graph 0.304, bm25_codes_id and routed 0.296). Hybrid with equal-weight RRF does not rescue them: 0.363 on paraphrase and 0.700 on no_code against dense's 0.917, because a course only dense ranks gets one vote and a course both retrievers rank gets two. The current routed system does not use dense at all, which is why routed scores 0.296 on paraphrases and 0.200 correctness on them.

**Router.** 110/115 in-sample. The router's patterns were written against the gold set, so that number describes coverage of phrasings already seen. The five prereq paraphrases g111 to g115 were written afterwards, in wordings the patterns do not cover ("ECEN 420 is required for what?", "what does ECEN 444 get me into?"), and the router routes 0/5 of them to the graph. All five then go to bm25_codes_id and the generator sees a truncated list. Correctness on those five is what the paraphrase prereq rows in the table measure.

**Generator drops the last item of long lists.** On g025 (17 gold courses) the answer omits ECEN 427 and on g063 (20 gold courses) it omits ECEN 403, in each case one course from a list the context contained in full. On g027 (5 gold courses) it omits CSCE 315, whose record lists CSCE 312 inside an "or" group rather than as a plain requirement. The judge scores all three 0 under the rule that omitting any gold course is incorrect; the human labeler accepted all three. These are the three disagreements behind the 0.900 judge agreement. Note from the author of this report: g025 and g063 drop the last course in the list, but CSCE 315 is second in g027's context, so "drops the last item" describes two of the three.

**The "list every course" prompt rule.** One rule added to the system prompt on 2026-09-13 told the generator to list every applicable course on require/unlock/follow-from questions. On the 100-question set of that day it moved overall correctness from 0.850 to 0.850, cut citation precision from 0.962 to 0.906, and lowered prereq correctness from 0.840 to 0.760. The generator started citing courses it mentioned in passing. Reverted the next day.

## Caveats

- Graph prereq recall is by construction: the prereq gold ids were derived from the same graph the retriever queries, so the claim rests on the prerequisite-string parser matching the catalog, which was checked by hand on 25 prereq rows.
- recall@5 is capped by gold-set size on prereq and multi_hop rows that have more than five gold courses, which is why recall@10 is reported alongside.
- Router patterns were written against the gold set, so the 110/115 is in-sample and the 0/5 on g111 to g115 is the only out-of-sample number.
- The paraphrase questions are at the hard end of what a student types; a real question usually carries a course code or a title word.
- The generator is pinned at temperature 0 and seed 0, and two fresh runs (cache bypassed) agreed on 100/100 answers and 100/100 verdicts.
- The judge cannot be pinned: Claude Sonnet 4.6 on this endpoint runs with extended thinking and rejects any temperature other than 1, but it showed zero drift across the same two fresh runs.
- The judge erred once on g024, scoring an answer 0 for "inventing" an ECEN 370 requirement that is in the ECEN 464 record; the identical answer scored 1 when rejudged after the rubric edit of 2026-09-14.
- Judge agreement is 0.900 on 30 human labels, and all three disagreements are list answers missing one course that the human accepted.
- g017 was relabeled after review; the human label now agrees with the judge that the answer omits the CSCE 221 prerequisite.
- The corpus is 148 courses, and recall will drop as it grows, because every added department adds distractors.

## Reproduce

Python 3.12 and uv. Retrieval needs no API key; generation needs `LLM_BASE_URL`, an API key, `LLM_MODEL` and `JUDGE_MODEL` in `.env` (see `.env.example`). Every LLM call is disk-cached under `data/cache/llm/`, so re-running an unchanged eval costs zero tokens.

```
uv sync --extra dev
uv run python -m catalog_rag.scrape --depts ECEN --depts CSCE
uv run python -m catalog_rag.chunk
uv run python -m catalog_rag.eval.run \
  --retrievers bm25 --retrievers bm25_codes --retrievers bm25_codes_id \
  --retrievers dense --retrievers hybrid --retrievers graph --retrievers routed \
  --generate --gen-retriever routed --gen-retriever bm25_codes_id
```

The eval writes `reports/<timestamp>.json` and `reports/latest.md`. `--fresh` bypasses cache reads to measure drift, and `eval.compare` diffs two report JSONs row by row.

CI (`.github/workflows/eval.yml`) runs on every push to main and every pull request: `uv sync`, `pytest`, then the BM25 retrieval eval if `data/processed/chunks.jsonl` is present, and posts `reports/latest.md` as a sticky comment on pull requests. As of this report the scraped files are gitignored and not committed, so the retrieval step is skipped in CI, and two tests in `tests/test_gold_files.py` that read `courses.jsonl` error there; the last three runs on main are red for that reason. Locally the suite passes.
